# nav: UAV-mapped-elevation-driven UGV navigation - Implementation Plan

**Package**: `nav` (`src/nav/`)
**Depends on**: `emap` (`src/emap/`) - consumes its published `/elevation_map`, imports `emap.traversability.LETHAL` and `emap.utils.gridmap_utils.decode_gridmap` directly (same colcon workspace).
**Reference (read-only)**: `src/d3/my_bot/` - the proven UAV+UGV pipeline this package replaces one piece of (pixel-color walkability classification) and otherwise reuses (PRM planning, Nav2 low-level following).
**Docs**: this file is the roadmap; `step01_...md` covers this milestone's full build+verification story.

## Why this package exists

`emap`'s roadmap (steps 1-12) proved the mapping side alone. The project's actual end goal is autonomous UGV navigation, so this milestone connects a UAV (which maps) to a UGV (which drives): classify the map into walkable/non-walkable space, plan a path through it, drive the path.

`src/d3/my_bot` already has a working version of this whole pipeline, but its walkability classification is a hardcoded BGR color-range threshold on a live top-down camera image (`waypoints_server.cpp`), tuned to one specific world's floor-gray rendering. This package replaces *only* that step with `emap`'s own already-tested `traversability` layer, and reuses d3's proven PRM planning algorithm and Nav2-based low-level following otherwise - see the full design discussion and the two explicit design decisions (walkability = traversability not elevation; unobserved cells excluded, not assumed safe) in `00_concepts.md`.

Not tested on the construction site (on hold) - a maze/room world ported from `src/d3/my_bot/worlds/roomWithObstacles.world` instead.

## Roadmap

1. **UAV-maps → walkable mask → PRM path → UGV follows** ✅ - see `step01_nav_pipeline.md` for the full build+verification story, including three real environment/API facts discovered live (not assumed) along the way:
   - **Nav2 isn't installed** in this environment (only `ros-humble-nav2-msgs`) - the full stack (`ros-humble-navigation2`, `ros-humble-nav2-bringup`) needed installing, same category of discovery as `emap`'s own "Gazebo Classic isn't installed" (`IMPLEMENTATION_PLAN.md`'s "Why restart"). Flagged to the user before installing (AGENTS.md's "never install unnecessary packages" rule), approved, and confirmed installed as of step 3 (found live via `ros2 launch`'s own process list - the full Nav2 lifecycle stack now comes up and activates cleanly).
   - **Ignition's `DiffDrive` system plugin uses LITERAL (unscoped) topic names** (`/cmd_vel`, `/odometry` - exactly whatever `<topic>`/`<odom_topic>` says), unlike `MulticopterVelocityControl`/`OdometryPublisher` (iris_quad's plugins), which auto-scope under `/model/<name>/...`. Confirmed by actually launching the world and publishing/echoing test messages - a bridge built on the assumed-scoped name would have silently connected to nothing.
   - **`DiffDrive`'s odometry is dead-reckoning from spawn, not world-absolute** - confirmed live (`nav_ugv`'s very first odometry reading was ≈(0,0) despite spawning at world (-0.7,-3.0), while iris_quad's `OdometryPublisher` reports true world-absolute pose under the same kind of frame name). Fixed with one static transform (`iris_quad/odom -> nav_ugv/odom`, translation = nav_ugv's actual spawn pose) tying the UGV's odom tree into the same frame `emap`'s map already publishes in, rather than inventing a separate "map" frame.
2. **Autonomous UAV demo mode + launch startup-race fix** ✅ - a real startup-ordering bug found from a live user run (Nav2 probing for a UGV that hadn't spawned yet, made worse by a badly-timed Ctrl+C) fixed with `TimerAction` staggering, matching `d3`'s own approach. Plus the requested "watch it run without controlling anything" mode: a small, honest 5-point hover patrol (`nav/autopilot.py` + `nav/uav_autopilot_node.py`, opt-in via `autonomous_uav:=true`) rather than a single static hover, since a single fixed vantage point can never fully see past `room_maze.world`'s interior walls - live-verified taking off, visiting multiple waypoints in sequence, and growing real map coverage, all without a single manual `/cmd_vel`. See `step02_autonomous_demo_and_launch_fixes.md`.
3. **Four real bugs found from an actual full user run, ending in the UGV actually driving** ✅ - `nav_ugv` spawning on a LETHAL cell (a permanent get_plan deadlock), a missing lidar static transform (every `/scan` silently dropped), the installed Nav2's `cmd_vel` output colliding with the UAV's own (fixed with `SetRemap`, not a fork of `navigation_launch.py`), and a UAV that could free-fall onto a bad landing (tipped ~90 degrees on one run) badly enough that no amount of correct control logic could recover - fixed at the root by restoring the safe near-ground spawn altitude every other `emap` world already uses, plus a proper world-to-body-frame conversion for the autopilot's velocity commands. Live-verified end to end: UAV takes off clean and level, `get_plan` finds a real path, and `nav_ugv`'s own odometry shows genuine continuous motion under Nav2's DWB controller. See `step03_real_bugs_from_a_live_user_run.md`.
4. **Two more real bugs found from a second live run** ✅ - a structural one: a parked `nav_ugv` is a physical object the UAV's depth camera has no notion of "not terrain" about, and fuses into its own elevation map, which could mark the UGV's own current cell LETHAL and permanently lock it out of ever planning a route away from wherever it's sitting. Fixed with standard costmap footprint-clearing (`prm_planner._clear_footprint_around`): the START point's own small footprint is always treated as passable, while the GOAL still must be genuinely walkable. Plus a data bug: the documented default goal `(4.0, 0.0)` sat ~0.1m from a real wall and could never be reached - replaced with `(1.7, -0.5)`, confirmed live. Live-verified: `get_plan` now succeeds in ~15s (down from 460s+) and `nav_ugv` drives continuously. See `step04_ugv_self_detection_and_a_bad_default_goal.md`.
5. **Frontier-aware tunnel navigation - a prototype, tested once, one limitation found honestly** ⚠️ - built to address a real gap flagged by the user: a region the UAV's overhead camera can never observe (e.g. a tunnel/culvert's interior) reads identically to a solid wall forever, even when it's the only route to a goal. Built four additive, off-by-default pieces (three-state walkable/lethal/frontier classification, frontier-aware PRM returning a tentative path, the UGV becoming a second mapping sensor via a new front-facing camera feeding the shared `/elevation_map`, and a periodic investigate-and-replan loop) - all unit-tested, all verified live to work correctly for genuinely unscanned space bordering known-walkable ground (the classical, literature-standard meaning of "frontier"). Live-testing against the literal "hollow tube" scenario it was commissioned for surfaced a deeper, structural finding: a solid opaque roof produces a *valid-but-wrong* elevation reading (the roof's own height), not an absence of data - a fundamental limit of any 2.5D single-height-per-cell map, not something this pass's mechanism (built around `is_valid=False`) can unlock. **Not promoted to be the default** - reported honestly per instruction ("test once, promote only if it works perfectly"). See `step05_frontier_tunnel_navigation.md` for the full live evidence and a concrete recommendation for what solving the literal case would actually require.
6. **Hybrid 2.5D + bounded 3D navigation - solving the literal occlusion case step 5 found** ✅ *all 6 phases complete* - step 5's root cause was representational, not algorithmic: a 2.5D grid cannot store two surfaces (a roof and the floor beneath it) at the same `(x,y)`. Rather than replace the proven, cheap 2.5D global map, add a second, bounded, persistent 3D voxel map that the UGV carries with it, consulted only where the 2.5D map itself flags doubt (a narrow, sharp elevation discontinuity bordered by walkable ground on both sides - a real signature distinct from a genuine wall). UAV keeps planning cheaply on 2.5D; UGV gets the only full-3D reasoning in the system, spatially capped (a configurable radius around the UGV, evicted every cycle, mirroring `emap` step 8's own local-vs-global map split one level up) so cost never grows unbounded. **Phase 1 (feasibility spike) done and live-verified**: `ros-humble-octomap-server` turned out to need root (unavailable in this environment - no sudo) - switched to the `octomap` PyPI binding instead (found and fixed two real bugs in that binding along the way: a `search()` null-handling gotcha and a catastrophic `deleteNode` default-depth bug). Both core claims confirmed live in `tunnel_test.world`: the octree correctly represents the tunnel's roof and interior as distinct voxels (the exact thing the 2.5D map cannot do), and bounded eviction kept the map's memory/extent flat even under an intentionally extreme 15m UGV drive. **Phase 2 (anomaly detection on the 2.5D map) done and live-verified**: `nav.anomaly.compute_anomaly_mask` flags the LETHAL-island-LETHAL shape a step-discontinuity artifact produces, distinguishing it from a genuine thin wall via a structural argument (a thin wall's interior never escapes to walkable at all) confirmed live at this world's own boundary wall. Found and fixed one real bug along the way: the tunnel's two step-edges turned out asymmetric in real sensor data (2 cells vs. 5 cells), which the original threshold missed entirely - fixed and pinned down with a regression test. Live-confirmed both the true positive (real tunnel mouths flagged) and true negative (real walls/open floor not flagged) against real `/elevation_map` data. **Phase 3 (anomaly-aware global PRM planning) done and live-verified**: `prm_planner.plan()` now returns a tentative path through anomaly cells when they're the only route, cost-penalized (20x) relative to frontier cells so a genuinely confirmed-safe alternate route is always preferred when one exists - unlike frontier cells, which carry no such preference since "unmeasured" isn't evidence of danger the way "scored LETHAL" is. Live-confirmed end to end in `tunnel_test.world`: `get_plan` from room A to room B returned waypoints through the tunnel's own anomaly island with `/plan_has_anomaly: True`. Found and fixed a real environment gotcha along the way (a leftover zombie `elevation_mapping_node` from an earlier phase's interrupted run was racing the fresh launch's own instance on the same topic - added to this project's growing "processes to check for" list). The risk-preference behavior itself (prefer confirmed over anomaly) is proven by deterministic unit test rather than live, since this test world's geometry has no alternate route to demonstrate the choice against - named honestly as the one live-evidence gap carried into Phase 4. **Phase 4 (local 3D verification) done and live-verified**: `nav.voxel_map.check_region_headroom` (built on Phase 1's map) now backs a real check `waypoint_follower` runs before advancing onto a tentative anomaly segment - live-confirmed, in one continuous run at the real tunnel coordinates, to answer "unknown" before the UAV's patrol had scanned the tunnel and "passable" once it had (a genuine before/after transition, not two separate claims). Found and fixed a real crash bug along the way: a `query_fn` calling-convention mismatch (`check_region_headroom` expects `query_fn(x, y, z)`; `BoundedVoxelMap.query` takes one `point_xyz` argument) killed `voxel_map_node` outright - and its whole accumulated map - the first time a real verification request arrived; fixed with a one-line adapter, a lesson that this kind of cross-module wiring needs at least one real live invocation, since unit tests of each piece in isolation didn't catch it. Two evidentiary gaps named honestly rather than hidden: the "unknown" state was proven via a manual, deliberately-early request rather than `waypoint_follower`'s own organic timing (same code path, different trigger - this world's timeline doesn't naturally linger in the unresolved window), and the "blocked" verdict is proven by unit test only, since `tunnel_test.world` has nothing genuinely impassable to demonstrate it against live. **Phase 5 (coordination loop) done and live-verified**: `nav.resolved_regions.ResolvedRegionStore` remembers every settled Phase 4 verdict and `planner_node` re-applies it to every future mask computation, so the same patch is never re-asked-about forever. Both halves confirmed live: a PASSABLE verdict, reported organically during a real run, made a later surgical query into that exact patch (start and goal both inside it) return a direct path with `/plan_has_anomaly: False` AND `/plan_has_frontier: False` - no longer tentative by either mechanism. A BLOCKED verdict (manually injected - this world has nothing genuinely impassable, same honest limitation Phase 4 already named) both triggered an immediate replan request and made a subsequent `get_plan` into that region genuinely fail (`no path found`) instead of offering it as a guess - closing the exact gap Phase 4 deliberately left open. One real, honest design tradeoff was surfaced, not hidden: the blocked override applies to the whole padded verification box (built generously for Phase 4's safety check), not just the precise anomaly cells - conservative and safe, but coarser than ideal. **Phase 6 (end-to-end acceptance run) done and live-verified, three times**: `tunnel_demo.launch.py` run fully hands-off, headless, end to end - the UGV starts in room A, crosses the tunnel's real coordinate range, and reaches the goal's immediate vicinity every single run (within 0.10m of the exact goal coordinate at closest approach in one run). Live-verified across 3 properly-instrumented runs (2 headless, 1 in the user's actual default GUI mode) using a strict settle-based success criterion (continuous 60s within Nav2's real 0.25m tolerance, not a single touch) - all 3 reached and stayed at the true goal. ## Ground rules (carried over from AGENTS.md / emap's own precedent)

- Reuse `emap`'s already-tested code wherever it fits (`traversability.LETHAL`, `decode_gridmap`) rather than re-deriving it.
- Reuse d3's proven algorithms (PRM sampling + line-of-sight + shortest path; Nav2/DWB following) - port and adapt, don't reinvent.
- Verify live against the real running system before trusting an assumption about plugin/API behavior - this project's discipline throughout `emap`, followed here for the DiffDrive topic-scoping and odom-frame findings above.
- No test/debug files in the repo root - everything under `tests/nav/`.
- Run simulations headless by default.
