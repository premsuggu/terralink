# nav: UAV-mapped-elevation-driven UGV navigation - Implementation Plan

**Package**: `nav` (`src/nav/`)
**Depends on**: `emap` (`src/emap/`) - consumes its published `/elevation_map`, imports `emap.traversability.LETHAL` and `emap.utils.gridmap_utils.decode_gridmap` directly (same colcon workspace).
**Reference (read-only)**: `src/d3/my_bot/` - the proven UAV+UGV pipeline this package replaces one piece of (pixel-color walkability classification) and otherwise reuses (PRM planning, Nav2 low-level following).
**Docs**: this file is the roadmap; `step01_...md` covers this milestone's full build+verification story.

## Why this package exists

`emap`'s roadmap (steps 1-12) proved the mapping side alone. The project's actual end goal is autonomous UGV navigation, so this milestone connects a UAV (which maps) to a UGV (which drives): classify the map into walkable/non-walkable space, plan a path through it, drive the path.

`src/d3/my_bot` already has a working version of this whole pipeline, but its walkability classification is a hardcoded BGR color-range threshold on a live top-down camera image (`waypoints_server.cpp`), tuned to one specific world's floor-gray rendering. This package replaces *only* that step with `emap`'s own already-tested `traversability` layer, and reuses d3's proven PRM planning algorithm and Nav2-based low-level following otherwise - see the full design discussion and the two explicit design decisions (walkability = traversability not elevation; unobserved cells excluded, not assumed safe) in `00_concepts.md`.

Not tested on the construction site (on hold) - a maze/room world ported from `src/d3/my_bot/worlds/roomWithObstacles.world` instead.

## Roadmap

1. **UAV-maps → walkable mask → PRM path → UGV follows** ✅ - see `step01_nav_pipeline.md` for the full build+verification story, including three real environment/API facts discovered live (not assumed) along the way:
   - **Nav2 isn't installed** in this environment (only `ros-humble-nav2-msgs`) - the full stack (`ros-humble-navigation2`, `ros-humble-nav2-bringup`) needed installing, same category of discovery as `emap`'s own "Gazebo Classic isn't installed" (`IMPLEMENTATION_PLAN.md`'s "Why restart"). Flagged to the user before installing (AGENTS.md's "never install unnecessary packages" rule), approved, and confirmed installed as of step 3 (found live via `ros2 launch`'s own process list - the full Nav2 lifecycle stack now comes up and activates cleanly).
   - **Ignition's `DiffDrive` system plugin uses LITERAL (unscoped) topic names** (`/cmd_vel`, `/odometry` - exactly whatever `<topic>`/`<odom_topic>` says), unlike `MulticopterVelocityControl`/`OdometryPublisher` (iris_quad's plugins), which auto-scope under `/model/<name>/...`. Confirmed by actually launching the world and publishing/echoing test messages - a bridge built on the assumed-scoped name would have silently connected to nothing.
   - **`DiffDrive`'s odometry is dead-reckoning from spawn, not world-absolute** - confirmed live (`nav_ugv`'s very first odometry reading was ≈(0,0) despite spawning at world (-0.7,-3.0), while iris_quad's `OdometryPublisher` reports true world-absolute pose under the same kind of frame name). Fixed with one static transform (`iris_quad/odom -> nav_ugv/odom`, translation = nav_ugv's actual spawn pose) tying the UGV's odom tree into the same frame `emap`'s map already publishes in, rather than inventing a separate "map" frame.
2. **Autonomous UAV demo mode + launch startup-race fix** ✅ - a real startup-ordering bug found from a live user run (Nav2 probing for a UGV that hadn't spawned yet, made worse by a badly-timed Ctrl+C) fixed with `TimerAction` staggering, matching `d3`'s own approach. Plus the requested "watch it run without controlling anything" mode: a small, honest 5-point hover patrol (`nav/autopilot.py` + `nav/uav_autopilot_node.py`, opt-in via `autonomous_uav:=true`) rather than a single static hover, since a single fixed vantage point can never fully see past `room_maze.world`'s interior walls - live-verified taking off, visiting multiple waypoints in sequence, and growing real map coverage, all without a single manual `/cmd_vel`. See `step02_autonomous_demo_and_launch_fixes.md`.
3. **Four real bugs found from an actual full user run, ending in the UGV actually driving** ✅ - `nav_ugv` spawning on a LETHAL cell (a permanent get_plan deadlock), a missing lidar static transform (every `/scan` silently dropped), the installed Nav2's `cmd_vel` output colliding with the UAV's own (fixed with `SetRemap`, not a fork of `navigation_launch.py`), and a UAV that could free-fall onto a bad landing (tipped ~90 degrees on one run) badly enough that no amount of correct control logic could recover - fixed at the root by restoring the safe near-ground spawn altitude every other `emap` world already uses, plus a proper world-to-body-frame conversion for the autopilot's velocity commands. Live-verified end to end: UAV takes off clean and level, `get_plan` finds a real path, and `nav_ugv`'s own odometry shows genuine continuous motion under Nav2's DWB controller. See `step03_real_bugs_from_a_live_user_run.md`.
4. **Two more real bugs found from a second live run** ✅ - a structural one: a parked `nav_ugv` is a physical object the UAV's depth camera has no notion of "not terrain" about, and fuses into its own elevation map, which could mark the UGV's own current cell LETHAL and permanently lock it out of ever planning a route away from wherever it's sitting. Fixed with standard costmap footprint-clearing (`prm_planner._clear_footprint_around`): the START point's own small footprint is always treated as passable, while the GOAL still must be genuinely walkable. Plus a data bug: the documented default goal `(4.0, 0.0)` sat ~0.1m from a real wall and could never be reached - replaced with `(1.7, -0.5)`, confirmed live. Live-verified: `get_plan` now succeeds in ~15s (down from 460s+) and `nav_ugv` drives continuously. See `step04_ugv_self_detection_and_a_bad_default_goal.md`.

## Ground rules (carried over from AGENTS.md / emap's own precedent)

- Reuse `emap`'s already-tested code wherever it fits (`traversability.LETHAL`, `decode_gridmap`) rather than re-deriving it.
- Reuse d3's proven algorithms (PRM sampling + line-of-sight + shortest path; Nav2/DWB following) - port and adapt, don't reinvent.
- Verify live against the real running system before trusting an assumption about plugin/API behavior - this project's discipline throughout `emap`, followed here for the DiffDrive topic-scoping and odom-frame findings above.
- No test/debug files in the repo root - everything under `tests/nav/`.
- Run simulations headless by default.
